# Цель

Нужно реализовать консольную Linux-программу для передачи файлов между двумя процессами.

Клиент и сервер должны быть частью одного исполняемого файла:

```text
file_transfer
```

Режим работы определяется аргументами командной строки.

Основной сценарий:

```text
server process
    |
    | TCP
    v
client process
    |
    v
file
```

Сервер постоянно работает и принимает соединения.

Клиент запускается только для одной передачи файла и после завершения работы завершается.

# Исходное ТЗ

## Обязательные требования

1. Сервер всегда находится в ожидании входящих подключений и приема файлов.
2. Клиент запускается только на время отправки файла.
3. Сервер сохраняет полученный файл в директории, где находится исполняемый файл.
4. Имя сохраненного файла должно иметь формат:

```text
date_time.hex
```

Используй однозначный машиночитаемый формат времени, например:

```text
20260930_130512_123456.hex
```

где присутствуют дата, время и микросекунды.

Расширение `.hex` является только требуемым расширением имени файла. Содержимое файла не нужно переводить в hexadecimal. Полученный файл должен быть побайтово идентичен исходному.

5. И сервер, и клиент должны явно сообщать:

   * начало передачи;
   * успешное завершение передачи;
   * ошибку передачи.

6. Сервер:

```bash
./file_transfer -s
```

7. Клиент:

```bash
./file_transfer -c /path/to/file
```

* Если передаётся флаг с кириллической `-с`, программа должна сообщить об этой ошибке;

## Будет плюсом

### 1. Несколько клиентов одновременно

Сервер должен уметь принимать несколько файлов одновременно от разных клиентов.

Используй простую и надежную модель:

```text
accept loop
    |
    +-- client worker #1
    |
    +-- client worker #2
    |
    +-- client worker #3
    ...
```

Допускается один поток на одно соединение.

Не делай сложный thread pool без необходимости.

### 2. Сервер не должен тратить CPU во время ожидания

Ожидание входящих соединений не должно реализовываться через busy loop или постоянный polling.

Допустимо и предпочтительно использовать блокирующий:

```cpp
accept()
recv()
read()
```

в отдельных рабочих потоках.

Сервер должен простаивать практически без нагрузки на CPU, когда клиентов нет.

### 3. Контроль ошибок передачи

Нужно обнаруживать:

* преждевременное закрытие соединения;
* невозможность прочитать очередной блок;
* ошибку записи на диск;
* повреждение переданных данных;
* несовпадение ожидаемого и фактически полученного размера;
* ошибку контрольной суммы;
* ошибки сокета;
* потерю клиента;
* невозможность завершить передачу.

При ошибке незавершенный файл не должен появляться как готовый `.hex`.

Используй временный файл:

```text
something.part
```

и только после полной успешной передачи выполняй атомарное переименование:

```text
.part -> .hex
```

Это позволяет гарантировать, что готовый `.hex` содержит только полностью принятый файл.

### 4. Абстракция транспорта

Архитектура должна позволять в будущем заменить TCP другим транспортом, например:

```text
TCP / Ethernet
COM-порт
Unix socket
```

Реализовывать COM-порт или другие транспорты сейчас НЕ нужно.

Но основной уровень передачи файлов не должен напрямую зависеть от конкретных вызовов TCP socket API.

Сделай четкое разделение:

```text
CLI
 |
Application
 |
Transfer protocol
 |
Transport interface
 |
TCP implementation
```

Например:

```cpp
class ITransport;
class ITransportListener;
class TcpTransport;
class TcpListener;
```

Имена классов можешь изменить, если предложишь более удачную архитектуру.

Главное требование:

`transfer` и `protocol` не должны знать о деталях TCP.

# Сетевой протокол

Не делай передачу вида:

```cpp
send(file_buffer);
```

или чтение "пока что-то пришло".

Нужен явно определенный бинарный протокол.

Он должен иметь:

1. magic;
2. version;
3. тип сообщения;
4. длину сообщения или payload;
5. размер файла;
6. контрольную сумму;
7. последовательность блоков.

Не используй C++ `struct` напрямую для отправки по сети из-за padding/alignment и зависимости от ABI.

Вместо этого явно сериализуй поля в network byte order.

Например, можно использовать следующую концепцию:

```text
HELLO
    magic
    protocol version
    file size
    whole-file CRC32
    chunk size

DATA
    sequence number
    payload size
    payload CRC32
    payload

FINISH
    total bytes
    total chunks
    whole-file CRC32

RESULT
    success / error
    optional error code
```

Это пример архитектуры, а не жесткое требование к именам сообщений.

Протокол должен быть документирован в:

```text
docs/PROTOCOL.md
```

## Важные свойства протокола

Передача должна быть потоковой.

Нельзя читать весь файл в память.

Используй фиксированный буфер, например:

```text
64 KiB
```

или разумный аналог.

Поддержи файлы размером больше 4 GiB, поэтому размер файла должен быть как минимум `uint64_t`.

Все чтение/запись должны корректно обрабатывать partial read/write.

Нельзя предполагать, что один `send()` отправляет весь буфер или один `recv()` получает весь пакет.

Сделай функции уровня:

```cpp
read_exact(...)
write_all(...)
```

или эквивалент.

# Контроль целостности

Используй CRC32 без сторонних библиотек.

Нужны:

```text
CRC32 всего файла
CRC32 отдельного DATA-блока
```

Это должно позволять обнаруживать повреждение данных на уровне прикладного протокола.

При несовпадении CRC сервер обязан:

* сообщить ошибку;
* не считать файл успешно принятым;
* удалить `.part`;
* оставить сервер доступным для следующих клиентов.

# Поведение при обрыве клиента

Особенно протестируй случай:

```text
server started
client starts
large file starts transferring
client process is killed
```

Сервер должен:

1. определить закрытие соединения;
2. вывести сообщение об ошибке передачи;
3. закрыть файловый дескриптор;
4. удалить временный `.part`;
5. не создать финальный `.hex`;
6. продолжить работу;
7. принять следующий клиент.

Это обязательный сценарий тестирования.

Реализовывать resume после обрыва не требуется, если это не нужно для выбранной архитектуры. Главное требование — корректное обнаружение обрыва и сохранение сервером работоспособности.

Сервер должен сохранять файл именно рядом с исполняемым файлом, а не просто относительно текущего working directory.

Например, запуск:

```bash

```

все равно должен сохранять файлы в директорию:

```text

```

Используй Linux-механизм определения пути к executable.

Нельзя использовать просто:

```cpp

```

Файл сначала пишется во временный:

```text

```

После успешной проверки:

```text

CRC32
protocol completion
```

выполняется rename в:

```text
YYYYMMDD_HHMMSS_ffffff.hex
```

Позаботься о коллизиях имен при одновременных клиентах.

Не допускай перезаписи уже существующего принятого файла.

# Интерфейс транспорта

Сделай абстрактный интерфейс для уже установленного двунаправленного соединения.

Например, концептуально:

```cpp
class ITransport {
public:
    virtual ~ITransport() = default;

    virtual void read_exact(std::span<std::byte> buffer) = 0;
    virtual void write_all(std::span<const std::byte> buffer) = 0;
    virtual void close() noexcept = 0;
};
```

А серверная сторона дополнительно имеет:

```cpp
class ITransportListener {
public:
    virtual ~ITransportListener() = default;

    virtual std::unique_ptr<ITransport> accept() = 0;
};
```

TCP будет одной конкретной реализацией.

Это лишь направление. Выбери окончательный интерфейс так, чтобы он:

* не зависел от TCP;
* был удобен для unit-тестов;
* позволял позже добавить COM transport;
* не содержал лишней абстракции.

# Потоки и многоклиентность

Серверный основной поток должен делать примерно:

```text
create listener
bind
listen

while (running):
    connection = accept()
    launch worker(connection)
```

Worker:

```text
read protocol
create .part
receive chunks
validate
close
rename .part -> .hex
```

Корректно синхронизируй:

* список worker threads;
* shutdown;
* генерацию имен;
* вывод в stdout/stderr.

Не допускай data races.

Если используешь detached threads, объясни почему. Предпочтительнее иметь контролируемый жизненный цикл потоков.

# Результат

Нужен полностью работающий репозиторий, а не набор рекомендаций.

Не ограничивайся:

```text
"вот архитектура"
"вот пример"
"дальше можно реализовать"
```

Нужно реально:

* создать исходники;
* создать CMake;
* создать тесты;
* создать README;
* создать документацию протокола;
* собрать проект;
* запустить тесты;
* исправить найденные проблемы;
* выполнить финальную проверку.

Не оставляй TODO вместо реализации.

Если требование неоднозначно, сначала используй наиболее простое решение, совместимое с ТЗ, и зафиксируй принятое решение в README или design note. Не меняй обязательный CLI.

В конце следуй формату отчета из `CLAUDE.md`:

* фактический triage;
* что реализовано;
* какие тесты запущены;
* результаты тестов;
* найденные и исправленные проблемы;
* итоговый статус `DONE`, `DONE_WITH_CONCERNS`, `BLOCKED` или `NEEDS_CONTEXT`;
* self-rating согласно `CLAUDE.md`;
* необходимые команды для запуска;

Главное: результат должен выглядеть как законченный production-quality кандидатный проект для тестового задания системного программиста, а не как учебный пример.
